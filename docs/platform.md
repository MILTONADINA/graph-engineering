# Graph Engineering platform

The platform extends the existing template registry with a local context engine and managed engineering runs. The CLI, MCP server, and browser dashboard use the same project configuration and project-scoped local stores. Context and operational history have separate SQLite databases. The template systems keep their separate metadata contracts.

## Start locally

Use Node.js 24, Git, and npm. Managed builds and tests additionally need a running Docker-compatible engine. Normal indexing and context retrieval do not require containers or cloud credentials.

```sh
npm ci
npm run build
npm run setup:git
npm run graph -- -C /path/to/project init
npm run graph -- -C /path/to/project index --lexical
npm run graph -- -C /path/to/project context 'Where is authentication handled?'
npm run graph -- -C /path/to/project serve
```

Open the printed loopback URL. Its fragment contains a local access token, which the dashboard stores only in the browser session. The server rejects unauthenticated API requests, non-loopback hostnames, and cross-origin requests. It is not a remotely exposed team service.

`.graph/project.json` is shared project configuration. Private data lives in the platform-specific user data directory under `graph-engineering/projects/<projectId>`; `GRAPH_ENGINE_DATA_DIR` can choose another root. Project IDs are stable across the partners' clones, while worktree and dirty-content identities keep source snapshots distinct.

## Context and memory

TypeScript/JavaScript, Python, Go, Rust, Java, and C# have bundled Tree-sitter grammars. Declarations, imports, and call expressions are indexed with explicit evidence. A pinned TypeScript compiler additionally resolves bounded TS/JS static bindings: relative named/default/namespace imports, unambiguous re-exports, direct function/constructor calls, and immutable identifier aliases. Compiler-proven edges carry `resolution: { kind: "static", engine: "typescript", version: "5.9.3" }`; these are declaration bindings, not proofs of runtime behavior. Remaining unshadowed same-file lexical candidates stay explicitly heuristic. Other text is searchable without claiming semantic language coverage.

The compiler runs in a separate worker using only indexed, hash-validated source and inert JSON/JSONC configuration in an in-memory host. Nearest-file `baseUrl`/`paths` aliases, bounded relative config inheritance, and uniquely declared in-repository workspace packages (`exports`, `types`, `main`) are supported with exact configuration provenance. It never executes plugins, reads configuration from disk, discovers `node_modules`, or fetches network content. Snapshot identity includes parser/compiler/resolver versions; source and configuration changes recompute cross-file bindings. Dynamic imports and dispatch, arbitrary object methods, overloaded or reassigned callables, ambiguous re-exports/conditional package targets, and implicit cross-file script globals remain unresolved. See [precise alias/package scope and privacy rules](context-lifecycle.md#memory-review-and-graph-limits); this is not full build-project selection or a configured type-check. Limits are 1,000 TS/JS files, 8 MiB source, 250,000 AST nodes, a 5-second worker deadline, and a 256-MiB old-generation heap limit, plus separately bounded configuration data. Exceeding a limit retains syntax/heuristic evidence and reports a coverage diagnostic; it does not claim complete semantic coverage. An unchanged fallback snapshot retains its diagnostic instead of silently retrying expensive analysis. `--lexical` skips embeddings, not this bounded source analysis.

SQLite stores revisioned records, FTS search, graph edges, and optional semantic vectors. Native database operations run in a dedicated worker thread. Ignored files, symlinks outside the project, excluded paths, credential patterns, and oversized/binary files are omitted. Credential patterns cover every PEM private key (including DSA, encrypted PKCS#8 and OpenPGP key blocks), AWS access key IDs, `sk-` API keys, GitHub tokens, live Stripe, Slack and Google API keys, bearer headers, named credential assignments (including quoted and unquoted values with punctuation, as in connection strings and DSNs, with interpolations, unquoted code and quoted key paths exempt) and passwords in URLs (judged after percent-decoding); in both, whole-value templates, masks and placeholder-only values are exempt, and a URL password that only begins with a template character is not. An assignment value that holds a `#`, an `@` or a generated word (digits back to letters twice, as in `Lm2Vx9Kp4R`) is not taken for code or a key path, but an unquoted value of ordinary words that starts with `{`, `[`, `(` or `!` or joins words with code operators is taken for code, and a quoted dotted passphrase of ordinary words (`Summer.Breeze2024x`) for a key path. Screening is heuristic, not a guarantee. Redaction of stored events and check output removes the same findings and is wider: any value of 12 or more characters after a password, API key, secret or access token name on the same line is redacted unless it is a whole-value template, mask, placeholder, interpolation or URL. Stored events keep the fields the engine reads back as recorded (the files a patch or step wrote, snapshot hashes and IDs), so a file whose name looks like a key is still verified and resumed; free text such as errors, summaries and check output is redacted. A private key header with no END marker, as in a truncated excerpt, is redacted through the end of the text. Omitted coverage is reported. Source hashes invalidate parsing and embedding caches; mandatory constraints cannot be silently dropped from context packets.

Python additionally has a bounded isolated CPython `ast`/`symtable` pass when a trusted local interpreter is available. It resolves direct lexical/import bindings without executing or importing repository code, and records the actual interpreter version and intermediate-source provenance. Unsupported runtimes and dynamic cases stay explicit fallbacks. See [Python coverage and process limits](context-lifecycle.md#isolated-python-bindings), including the sampled—not instantaneous—macOS memory watchdog. Go adds a fixed packaged `go/types` helper for direct functions and represented module/workspace imports; it compiles only that helper, never repository code, and retains complete package/config/dependency provenance. See [Go coverage and process limits](context-lifecycle.md#snapshot-only-go-bindings). Java adds fixed `javac` snapshot analysis with no annotation processors or target execution; C# adds SDK8 Roslyn analysis without MSBuild, generators or target execution. See [Java](context-lifecycle.md#snapshot-only-java-bindings) and [C#](context-lifecycle.md#snapshot-only-c-bindings) for exact subsets, project restrictions and resource limits. Rust adds pinned rust-analyzer LSP declaration navigation through an isolated edition-2021 source snapshot, with no Cargo or target execution. Its verified runtime is currently Linux-fixture-only, not provisioned on Mac/Windows; see [Rust subset and limits](context-lifecycle.md#snapshot-only-rust-bindings). None of these passes establishes complete multi-language runtime semantics.

Semantic retrieval uses pinned local Jina code embeddings. Weights are an explicit download of approximately 642 MB; ordinary startup/index/search never downloads them. Asset hashes are checked before offline runtime loading. Use `embeddings-provision` only after allowing the documented model distribution hosts in project network policy. `index --lexical` builds source, graph, and summaries without invoking embeddings; ordinary `index` computes available semantic vectors. Hybrid retrieval lazily fills missing vectors, so its first request can be substantially slower than a cached query. The context API also supports lexical-only and graph-expanded retrieval; absent weights produce an explicit semantic-unavailable fallback.

Deterministic file/directory/repository summaries use content hashes, not generative summarization. `summaries` exposes these bounded structural summaries. `memory-review` flags stale evidence, lexical possible contradictions and exact conflicts between [explicit reviewed assertions](memory-assertions.md), without choosing a winner. Typed assertions compare declared scope, value and validity; they cannot prove that an architectural claim is correct or obsolete.

```sh
npm run graph -- -C /path/to/project memory-add 'Preserve the existing public API' --kind constraint --source src/index.ts#L1-L40
npm run graph -- -C /path/to/project memories
npm run graph -- -C /path/to/project memory-accept MEMORY_ID
npm run graph -- -C /path/to/project memory-reject MEMORY_ID --reason 'Why not'
npm run graph -- -C /path/to/project memory-share MEMORY_ID
npm run graph -- -C /path/to/project memory-export-authorize MEMORY_ID
npm run graph -- -C /path/to/project memory-export-authorize MEMORY_ID --sha256 HASH
npm run graph -- -C /path/to/project memory-add 'Preserve the public API of v2' --kind constraint --source src/index.ts#L1-L52 --supersedes MEMORY_ID
```

New memories are private proposals. Acceptance makes a record usable as project knowledge; rejection (with a reason) keeps it on record but never usable; sharing writes a reviewable `.graph/knowledge/<id>.json` file without committing it. `--source <path>#L<start>-L<end>` (repeatable) cites lines of a file as evidence, resolved against a fresh index snapshot; a missing or unindexed file, or lines past its end, are refused. `--supersedes <id>` proposes a successor: accepting it retires the accepted memory it names (status `superseded`, history kept). Competing/cyclic imported successors remain unresolved. Stale or conflicted mandatory constraints are preserved for review, never silently removed. Private mandatory memories block cloud context export rather than disappearing from a task. Sharing is not export authorization: a cloud consumer receives a mandatory memory only when it cites source evidence inside `exportPaths`, is shared, and an operator has reviewed its exact text with `graph-engine memory-export-authorize <id>` and recorded consent with `--sha256 <hash>`; until then the whole packet is refused. The refusal names each blocked memory and the command that unblocks it: `memory-share`, `memory-export-authorize`, or, for a memory with no exportable evidence, a sourced successor proposed with `memory-add --source <path>#L<start>-L<end> --supersedes <id>` ([the full flow](memory-assertions.md)). `graph-engine memory-export-revoke <id>` withdraws that consent, including for runs already in progress: a run reads the authorization again before each cloud worker turn, so its next cloud turn is refused.

### Storage lifecycle

```sh
npm run graph -- -C /path/to/project summaries
npm run graph -- -C /path/to/project memory-review
npm run graph -- -C /path/to/project watch --interval 5000
npm run graph -- -C /path/to/project snapshots-prune --keep 20
npm run graph -- -C /path/to/project backup /path/to/private-backups/new-archive
npm run graph -- -C /path/to/project restore /path/to/private-backups/new-archive /path/to/new-private-data
```

`watch` reconciles full source hashes with backpressure; it is not an mtime-only cache. Snapshot pruning previews by default; `--apply` is required for deletion. It retains the requested newest snapshots plus current/per-worktree context and memory/plan evidence. Private source payloads are currently repeated across snapshots, so retention matters. Migrations reject unknown newer schemas instead of attempting a downgrade.

`backup` creates a new private archive containing context, run history, the nullable usage ledger, and validated provider/decision/promotion configuration. It refuses active runs and detects concurrent run-store/config changes. `context-backup FILE` is the narrower context-only operation. Restore verifies hashes, project identity, schemas, SQLite integrity, and plan snapshot references, and only writes a **new** destination directory. It does not switch the running service to that directory or overwrite repository configuration. Model weights, workspaces, environment files, and raw credential configuration fields are excluded; existing private database history is preserved. Archives are private plaintext, not encrypted or cryptographically signed. Restored work requires explicit reconciliation, not blind replay.

See [context lifecycle](context-lifecycle.md) for API signatures, limits, backup scope, and the measured 10,000-file synthetic indexing receipt. That benchmark is not a coding-quality, semantic-retrieval, or token-savings evaluation.

## MCP clients

Configure the installed CLI as a stdio MCP server:

```json
{
  "command": "node",
  "args": [
    "/absolute/path/to/graph-engineering/packages/engine/dist/cli.js",
    "-C",
    "/path/to/project",
    "mcp",
    "--client",
    "cloud"
  ]
}
```

Use `--client local` only for a consumer whose inference actually stays local. Cloud-backed clients are refused for offline projects. Cloud graph lookups apply the export allowlist to seeds and both resolved endpoints before traversal, so non-exportable files cannot disclose target identifiers or connect otherwise separate public nodes. MCP exposes context, symbols, graph relationships, templates, memory proposals, and run status, list and events; cloud clients see run status and list only when the server runs with `--allow-run-status`, their `run_list` omits objectives, and their `run_events` carries each event's type, time and step without its data. `--allow-run` separately enables `plan_decompose` (a planner proposes steps; [proposed decomposition](decomposition.md)), `plan_create` (acceptance criteria required), `run_start` and `run_cancel`, so a connected AI can break work down, plan, start, follow (`run_events` until `complete`) and stop a run. `run_events` also notices a run whose owning process died (a crash of `graph-engine run`, or a kill it cannot handle) and records it as `needs_reconciliation`, as every engine start does, so a client polling it does not wait forever. A cloud-backed client can decompose and create plans only while publication is `none`, and its planner sees only exportable context. A plan it creates must also run its worker steps, the configured tester and the configured reviewer all on local providers or all on non-local ones, since a local step could otherwise copy a file the export policy keeps private to an exported path where a cloud worker or reviewer receives it; a person's own plan may mix them. When `run_start` refuses a publishing run because Git skips checking files in the checkout, a cloud-backed client gets only their count; the command line and a local client also get their names. A plan that publishes (commit or draft PR) cannot be started over MCP or the dashboard API until a person reviews it with `graph-engine plan-approve <planId>` and approves it with `--yes`, an approval bound to the plan's exact content; `graph-engine run` counts as the person's approval ([plan approval spec](../specs/integration/plan-approval.md)). Resuming a stopped run needs a person to acknowledge its retained state (`graph-engine resume --reconciled` or the dashboard), so MCP offers no resume. MCP does not replace a native client's own permissions or intercept all its model calls.

The owner currently authorizes selected source/docs, not blanket shared-memory or operational-metadata export. Cloud `context_get` and Graph-managed cloud worker dispatch refuse, before returning or dispatching anything, a packet whose mandatory memory is private, unsourced, outside `exportPaths`, altered, or not authorized for its exact text, and a cloud packet with no memory provenance. Path and credential-pattern filters cannot prove arbitrary allowlisted source is secret-free.

`exportPaths` is an allowlist of globs. An entry starting with `!` is an exclusion: a path is exportable when some other entry matches it and no exclusion does, so `["src/**", "!src/internal/**"]` exports `src/` except `src/internal/`, and a list of exclusions alone exports nothing. `!` on its own and entries starting with `!!` are refused when the project loads. A step's `writes` globs (and a tester's) follow the same rule and must include at least one entry that is not an exclusion. `excludedPaths` entries are matched one at a time, so a `!` entry there excludes everything outside its pattern and never re-includes a path. Each side errs toward exporting less. Inclusions are case-sensitive, and a slash-free inclusion such as `*.md` means the top level only. Exclusions ignore case, and a slash-free exclusion such as `!*.pem` applies at any depth, as in `excludedPaths`. Names are compared in Unicode NFC, so an exclusion typed `café` also covers a file stored in the decomposed form common on macOS. Because macOS and Windows file systems are usually case-insensitive, a cloud worker's source request is served only when every part of the path has exactly that name on disk (Unicode form aside) and the name on disk is itself exportable, so a request for `notes/plan.md` never returns `notes/plan.MD`. When the planner is local but a cloud worker implements the proposed steps, the planner also gets only exportable context, since its step text reaches the cloud worker.

## Configure workers

Providers are machine-local configuration, while the project policy determines which providers and source paths are allowed. Credentials are read from named environment variables and are never stored in project configuration.

```sh
npm run graph -- -C /path/to/project provider-add qwen local YOUR_LOCAL_MODEL --endpoint http://127.0.0.1:11434/v1 --input-cost 0 --output-cost 0 --enable
npm run graph -- -C /path/to/project check-add node:24-alpine node --test test.cjs
npm run graph -- -C /path/to/project plan 'Fix the failing addition test' --accept 'The addition test passes' --provider qwen
npm run graph -- -C /path/to/project run PLAN_ID
```

`provider-add` stores a worker's whole configuration, replacing any worker with the same ID, and permits a local worker. A cloud or installed worker needs `--enable`; to permit a worker that is already configured, run `provider-enable <id>`, which adds it to `policy.providers` and leaves its endpoint, key variable, prices, efforts and limits unchanged. The program's own options, such as `-C <project>`, go before the command. Under a numeric `policy.maxCostUsd` (the checked-in project uses 0), planning refuses a worker without recorded prices, including a local one, so the example records a local worker's prices as zero with `--input-cost 0 --output-cost 0`; `provider-add`, `provider-enable`, `reviewer` and `tester` warn about a worker the cap would refuse for that reason. Register checks with `check-add` before planning: a plan keeps the verification commands configured when it was created, so `plan` (and `plan_create` and the dashboard) warns about a plan with none, and `run` refuses it and, once checks exist, says to create a new plan.

The local endpoint must support OpenAI-compatible chat completions and structured JSON responses. Graph Engineering does not install or assume a particular generative model. Cloud API providers use `openai` or `anthropic`; configure their model, supported efforts, and credential environment variable explicitly. Installed-agent capability restrictions are described in `installed-workers.md`.

To enable cloud API workers, review `.graph/project.json`: its checked-in inference/network mode is already `allowlisted`, but only local `qwen`/`laya` providers are permitted and no outbound hosts are listed. Add explicitly reviewed cloud provider IDs and exact HTTPS hosts, and review the selected exportable file patterns before use. Do not use wildcard network hosts. A strict cost budget requires known pricing and a compatible API worker; missing telemetry is unknown, not zero.

Cost-capped Jev calls require reviewed bounded request/question pricing and a persistent pre-dispatch reservation. Without known pricing or ledger capacity, they abstain. Every dispatched batch has one call identity; its cost is not counted once per question. Unknown usage, legacy untracked calls, and unresolved charges remain `null`, while known subtotals and reservations remain visible in the dashboard. The ledger includes planning-only and failed calls as well as completed runs. These are conservative client-side estimates and reported charges, not a provider-enforced financial guarantee. See [decision accounting](decisions.md#jev-accounting-and-budgets).

The worker proposes exact-substring patches or asks for specific missing files. The engine validates the entire proposal before editing its isolated worktree: a proposal that uses one path as both a file and a directory, or spells one file two ways, goes back to the worker as feedback, and a write that fails partway (for example a full disk) is rolled back so no file the run did not record is left to escape review and reach publication. A patch that leaves a file the run wrote outside the verification inventory (a new Git-ignored file, or ignore rules that hide an earlier file) is rolled back too, so `resume --reconciled` asks the worker again instead of failing on the same file. The patch is recorded as applying before its first write, so if the engine stops mid-write, or the rollback cannot restore the pre-patch workspace (which then needs reconciliation), the files it left count as the run's: they are reviewed, security-scanned and held to the verification inventory on resume. Original files remain untouched. Sequential worker steps can reuse a previously verified proposal for matching objective/acceptance, provider/model, verification configuration, policy, step write scope, and exact snapshot; a cached proposal that changes a file outside the step's write scope is never applied. Cache replay validates the proposal and reruns required checks; it never treats old test success as current proof. Changed inputs, policy, parser version, or source snapshot invalidate the context solution cache. This is exact evidence-backed reuse, not fuzzy retrieval of arbitrary old fixes.

Verification runs against a separate source view in a provisioned container with no external network, credentials, repository metadata, or private configuration mounted. Verification inputs must remain unchanged during checks; an input a check replaces with anything other than a regular file, such as a FIFO, fails verification as a changed input instead of being read. Preload dependencies into the verification image when a build needs them; the engine never silently installs packages from the network. [Verification images](verification-images.md) has recipes for Maven, Gradle, Node.js and Python.

Verification resolves local image tags to immutable image IDs and records that identity. Detailed failure excerpts stay local; cloud/native workers receive generic check-failure feedback because logs may contain non-exportable source. They may request additional explicitly exportable files, whole or as `path#L<start>-L<end>` line ranges; a file too large to send whole returns an outline of its symbols and line ranges ([worker context excerpts](worker-context-excerpts.md)). A request naming a path they may not receive, or one whose name looks like a credential, is refused before any file is read, by export policy and credential screening alone, and answered once with feedback that names only the paths the worker sent (counting, not naming, a credential-like one, since feedback holding a potential secret is never dispatched); a second such request stops the step. A cloud implementer is told only of the tester's files it may request. This trades some debugging convenience for an enforceable export boundary.

`run`, `resume` and `review-approve` wait for the run and print its record, then exit 0 only when it succeeded: 1 when it failed or was cancelled (the same code as any command error) and 2 when it needs reconciliation. So `graph-engine run PLAN_ID && next-step` goes on only after a run that succeeded. Ctrl-C or SIGTERM while one of them waits cancels the run: checks and installed agents run in their own process groups, which the terminal's Ctrl-C does not reach, so the command stops them, kills and removes the check containers, records the run as `cancelled` (or as `needs_reconciliation` when its publication had started; see below), prints it and exits 130, or 2 when the run needs reconciliation. A run that had finished before the cancel reached it also exits 130. A run still being set up when Ctrl-C arrives is never started or resumed. A repeated Ctrl-C is ignored until that cleanup has finished.

Runs preserve structured events and failures. A changed policy or source snapshot invalidates dispatch. Cancellation stops further work; a run cancelled once publication has started stops as `needs_reconciliation`, since its commit, push or pull request may already exist. Only the current attempt's publication counts: after `resume --reconciled` acknowledges an earlier attempt's, an attempt that fails or is cancelled before publishing again stops as `failed` or `cancelled`. After a crash or failed attempt, inspect the retained worktree and events before `resume RUN_ID --reconciled` (`run-receipt RUN_ID` reads them without opening the engine or triggering recovery); ambiguous external effects are never blindly repeated. Automated completion leaves human acceptance pending and records required review scope, on a run whose publication succeeded; a run that stops after its checks passed carries no pending acceptance. A test pass or classifier confidence is not human acceptance, a completed security audit, or merge approval.

## Publication

Publication defaults to `none`. To enable it, choose `commit` or `draft-pr` and configure a GitHub repository, remote, and `dev` base branch. Git and `gh` use the user's supported local authentication. The original worktree must be clean before a publishing run, and before resuming one whose workspace was never created, so unrelated edits cannot enter its commit; the source snapshot cannot stand in for this check because it leaves out binary, large and credential-like files. Untracked files count even when Git is set to hide them (`status.showUntrackedFiles=no`), both for this check and when publication decides whether a run changed anything, so a change made only of new files is committed. Both steps also refuse files Git skips checking for changes, those marked assume-unchanged or marked skip-worktree while on disk, since status cannot see a change to them; clear the marks with `git update-index --no-assume-unchanged` or `--no-skip-worktree` first. The refusal before a run starts counts those files and names them only on the command line and to a local MCP client (`git ls-files -v` lists them with a lowercase tag or `S`), since a cloud-backed MCP client may have started the run. `core.ignoreStat=true` sets that mark on every file Git checks out, so the engine's own Git commands turn it off and a run's worktree never gets it; a checkout already marked by it is refused. A skip-worktree file a sparse checkout leaves off disk is not a hidden change. Draft PRs require explicit GitHub network permission. Main/master push and PR targets are rejected. Merging and publishing releases remain human actions.

Managed Git operations suppress repository hooks, executable filters, filesystem monitors, stat-skipping (`core.ignoreStat`), and signing programs. Publication verifies the actual staged bytes against the checked source. Files requiring Git LFS/custom clean filters or checkout normalization may need manual publication; the engine fails closed instead of committing bytes different from those verified. Interrupted publication reconciles run-owned commits and existing PRs after explicit review and reverification.

```sh
GRAPH_ENGINE_DOCKER_TESTS=1 npm test -w @graph-engineering/engine
```

The optional embedding integration test uses real weights, downloading them only when its explicitly configured cache is missing; default tests remain offline. Existing generated-app builds and executable fine-template container checks have opt-in smoke tests. Synthetic fixtures and protocol tests cannot enable promotion. The repository does not ship fabricated success-rate or token-savings claims. ## Template adapters and bounded decisions

`templates` lists separate `scaffold:` and `graph-node:` namespaces. `scaffold CONFIG TARGET` previews the existing coarse-grained generator; add `--write` to materialize it without automatic dependency installation. `validate-graph ARTIFACT_DIRECTORY` checks fine-grained graph schemas, implemented-node status, distinct invocation IDs, dependency bindings, order, cycles, manifests, and required artifact coverage.

All 53 implemented catalog nodes have audited deterministic proposal renderers, including backend/CRUD, full-text search, webhook ingress, authentication/authorization, database lifecycle, storage, project/frontend scaffolds, documentation, testing and DevOps. They validate schemas, package/export prerequisites, bounded values, exact shared-file edits and generated paths, then propose artifacts for sandbox verification. They do not install dependencies or run template hooks on the host. The ECS Express Mode composer emits only an offline plan and private request, never deploys. Public examples and root ledgers require [explicit policy permissions](public-template-artifacts.md); private memory and engine control state remain protected. The three planned nodes remain unavailable. See the [coverage inventory and security limits](dag-and-template-runtime.md#remaining-catalog-inventory); capability is not deployment, provider compatibility or human acceptance.

`plan OBJECTIVE --accept CRITERION --steps reviewed-steps.json` accepts an explicit dependency DAG with per-step workers or supported templates. Ready proposals run concurrently within policy capacity; patch application is serialized, overlapping independent write sets are rejected, and checkpoints bind plan/policy/workspace identity. A patch that fails after application, including a repair patch after failed combined checks, is rolled back; a crash mid-application is resolved on `resume --reconciled` only when the workspace matches the step's pre-patch or post-patch fingerprint, and the files of a step recorded as applied are reviewed and security-gated like any other. The service also reserves project-wide worker slots and inference budget. A worker dispatch is recorded only once its call holds a slot and its reservation, so a run cancelled or timed out while waiting for a slot can still be resumed. Releasing a slot and marking an interrupted run take the database's write lock up front, so another process writing at that moment makes them wait rather than fail. New run and worker leases bind to a process-instance proof, so a reused PID cannot validate them. Legacy PID-only leases retain a live PID conservatively during an in-place upgrade; if that PID was reused, an operator must reconcile the lease manually. This is a bounded scheduler, not automatic decomposition of every engineering request into a proven architecture. See [DAG and template runtime](dag-and-template-runtime.md).

Controllers cover worker/workflow/effort/context budget, retrieval scope, context/file/memory selection, tool/test/review scope, retry/escalation, stopping, and memory-write proposals. Independent questions are batched (up to 12 per provider request); dependent stages remain separate. A cascade sends only unresolved questions onward. Mandatory evidence, required checks, review floors, and the audit log cannot be removed by a classifier.

Shadow predictions do not change deterministic selections. Promoted choices need category-specific evidence and must remain in the policy-allowed candidate set; explicit worker/effort selections take precedence. Hosted decisions additionally require separately reviewed exportable state and question metadata. No classifier can grant network/file permissions, prove a patch correct, approve a merge, or invent arbitrary architectural alternatives. Routing quality, failures, retries, and total measured cost must be evaluated together before enabling autonomy.
